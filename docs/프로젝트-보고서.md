# 프로젝트 보고서 — "생동하는 기록(Living Record)" 앱 만들기

> 학생용 학습 프로젝트 · 작성 2026-06-05 · 플랫폼 iOS 26+ (Swift/SwiftUI/SwiftData)
> 이 문서는 한 앱이 *구상 → 검증 → 67개 커밋*을 거쳐 완성되는 전 과정을, **하나씩 다시 공부할 수 있게** 정리한 보고서다.
> 같이 읽을 설계 문서: `concept.md`(결정 토론) · `spike-findings.md`(기술 검증) · `v1~v4-slices.md`(작업 계획) · `사용설명서.md`(완성본 사용법)

---

## 0. 이 프로젝트로 무엇을 배우나

겉보기엔 "음성 메모 앱"이지만, 학습의 진짜 목표는 **앱 하나가 만들어지는 사고의 흐름**이다.

**학습 목표**
1. **수직 슬라이스**로 기능을 쪼개 *작동하는 앱*을 한 단계씩 키우는 법.
2. **불확실한 기술은 코드 전에 스파이크(실험)로 검증**하는 습관.
3. AI(온디바이스 LLM·임베딩)를 **믿을 수 있는 만큼만** 쓰고, 못 믿는 부분은 **결정적 규칙**으로 보완하는 판단.
4. **프라이버시·데이터 소유권**을 처음부터 설계에 박는 법.
5. **실패에서 배우기** — 되돌린 기능, 버린 접근, 고친 버그가 이 프로젝트의 가장 값진 교재다.

**핵심 가치(앱이 답하려는 질문)**: *"나는 무엇을 지속할 것인가?"* — 흩어진 생각을 모아, 무엇을 이어가고 무엇을 놓을지 사람이 결정하도록 *증거*를 보여주는 앱.

## 1. 개발 방법론 (모든 단계에 관통하는 원칙)

이 프로젝트가 따른 작업 규율. **단계마다 똑같이 반복된다.**

| 원칙 | 뜻 | 어디서 드러나나 |
|---|---|---|
| **수직 슬라이스** | UI~저장까지 한 흐름을 관통하는 최소 단위로 작업 | S0~S15, 각 커밋이 *작동하는* 한 조각 |
| **스파이크 우선** | 불확실한 기술은 본 구현 전 작은 실험으로 검증 | `spike/` 24개, `spike-findings.md` |
| **구현 → 실행 검증 → 커밋** | 빌드만이 아니라 *실제로 돌려보고* 커밋 | 모든 feat 커밋 |
| **결정은 사람이** | AI는 증거 제시까지, 판단은 사용자 | 지속/보류/접기, 큐레이션 |
| **결정적인 건 결정적으로** | AI가 못 믿을 부분은 규칙으로 | 의도 어미 게이트, 날짜 창 |
| **프라이버시 우선** | 로컬 기본, 클라우드는 옵트인·증류층만, 봉인 | 2단계 증류, 봉인 폴더 |
| **문서로 결정을 남긴다** | 왜 그렇게 정했는지 토론·근거를 기록 | concept/spike/slices 문서 |

> **학습 포인트:** 좋은 코드보다 *좋은 판단의 기록*이 먼저다. 이 앱의 docs 폴더가 코드만큼 중요한 이유.

## 2. 기술 스택 (학습 대상 기술)

## 페이즈 0 — 구상과 검증 (코드 0줄)

### 단위 0-1. 무엇을·왜 만드나 (구상)
- **목표:** 막연한 아이디어를 *결정된 사항*과 *미결*로 가르기.
- **핵심 개념:** 차별점 정의("무엇을 지속할까"), 프라이버시 하이브리드, 2단계 증류, 분류=주제(emergent+통합).
- **읽을 것:** `concept.md` 전체.
- **배울 점:** 코드 전에 *토론으로 결정을 고정*한다. 바뀌면 문서를 갱신한다.
- **복습 질문:** 이 앱이 "음성 메모 + AI 요약"과 다른 단 하나는? 봉인(sealed)은 어떤 문제를 푸는가?

### 단위 0-2. 스파이크 — 하드 파트 먼저 검증
- **목표:** "Apple 온디바이스 AI가 *한국어로* 쓸 만한가?"를 본 구현 전에 실측.
- **핵심 개념:** 스파이크(throwaway 실험), 가설→측정→판정.
- **읽을 것:** `spike-findings.md` ①~⑧, `spike/` 폴더(24개).
- **핵심 발견:**
  - ① 임베딩: 한국어 OK, **단 중심화 전처리 필수**(안 하면 다 몰림).
  - ② STT: 신형 **SpeechTranscriber** 확정(레거시 버림). 실음성 문자정확도 92.8%.
  - ③ FM 가드레일: 무해한 교사·아동 문장도 거짓 차단 → 폴백 필요.
  - ⑥ 주제 자동분류: 온디바이스 FM 불안정(과병합↔과분할) → **best-effort + 큐레이션**.
- **배울 점:** *불확실하면 작게 실험해 사실을 손에 쥔 뒤 설계한다.* 스파이크는 버리는 코드라 빨리 쓴다.
- **복습 질문:** 중심화(centering)는 왜 필요했나? FM을 못 믿는다는 걸 어떻게 *측정*했나?

## 페이즈 8 — 실패·점검에서 배우기 (이 프로젝트의 백미)

### 단위 8-1. 양방향 Obsidian — 도입했다 철회한 사고
- **무슨 일:** 양방향(가져오기·삭제·자동 동기화) 도입(`184c6a9`) → **중복 생성 사고** → 철회(`59f559c`).
- **근본 원인:** 기존 미러 `.md`엔 `id:`가 없어, 가져오기가 그것들을 *전부 새 포착*으로 만들어 **라이브러리 통째 복제.**
- **배울 점(중요):**
  1. **삭제·자동 동기화는 위험.** 명시적·안전장치·dry-run이 기본.
  2. id 없는/모호한 파일을 "새 것"으로 만들면 안 됨 → 별도 inbox·해시 매칭.
  3. *되돌릴 줄 아는 것*도 실력. 철회를 깔끔히(잔재 주석까지) 정리.
- **읽을 것:** 커밋 `184c6a9`(도입) ↔ `59f559c`(철회) diff 비교.
- **복습 질문:** 왜 "전체 다시 내보내기 먼저" 안내만으론 부족했나?

### 단위 8-2. 임베딩 한계 — 세 번 확인한 교훈
- **무슨 일:** 주제 군집화(S4) → 주제 연결(S10) → 위키 관련 주제(7-3), **세 번 다 임베딩 순위가 거칠어** 신뢰 못 함.
- **배울 점:** 한 기술의 한계를 *반복적으로 만나면* 그 신호 자체를 포기하거나 결정적 대안으로. "임베딩=만능"이 아님.

### 단위 8-3. 전체 점검 — 코드 리뷰와 프라이버시
- **무슨 일:** 막바지 코드 리뷰에서 **기간 정리가 봉인 주제명을 클라우드로 보내던 누수** 발견·수정 + 죽은 코드 제거 + 경고 0.
- **파일:** `PeriodReview.swift`(`!sealed` 필터), `Interfaces.swift`(스텁 제거). **커밋:** `232fa5a`.
- **배울 점:** *프라이버시 불변식은 끝까지 검증한다.* "클라우드로 가는 모든 경로에 봉인이 빠지는가?"를 체크리스트로.
- **복습 질문:** 일일/주간 로컬 정리는 봉인을 *포함*하는데 왜 그건 두기로 했나?(클라우드 vs 로컬의 차이)

## 6. 학생 과제 (제안)

**A. 따라 만들기(필수)** — S0~S4까지 직접 구현. 포착→저장→목록→주제 묶기까지.

**C. 판단 분석(에세이)** — 다음 중 하나를 골라 "무엇을·왜·어떻게 결정했고, 나라면?":
- FM Bool 대신 어미 게이트를 택한 이유 (단위 2-1)
- 양방향 Obsidian 철회 (단위 8-1)
- 임베딩 관련 주제 제거 (단위 7-3)

**D. 확장(택1)** — 미구현/철회 항목을 *안전하게* 다시 시도:
- '같은 날 함께 등장' 결정적 관련 주제
- 임계값 튜닝(냉각·다짐·모멘텀)을 실데이터로
- iCloud 동기화 또는 MLX 폴백 본체

**E. 프라이버시 감사** — "봉인이 기기를 떠날 수 있는 모든 경로"를 코드에서 추적해 표로. (힌트: 클라우드 vs 볼트 iCloud 동기화)

- **스파이크**: 불확실성을 없애려 빠르게 짜고 버리는 실험 코드.
- **봉인(sealed)**: 기기 밖으로 안 나가는 포착(클라우드·갤러리 제외, 별도 폴더).
- **2단계 증류**: 원문→(로컬 추상화)→증류층→(옵트인)클라우드.
- **중심화(centering)**: 임베딩이 한쪽에 몰리는 현상(anisotropy)을 평균 빼서 보정.
- **best-effort + 큐레이션**: 자동은 출발점, 정리는 사람이.
- **결정적 게이트**: AI 대신 규칙(한국어 어미 등)으로 판정 — 환경에 안 흔들림.
